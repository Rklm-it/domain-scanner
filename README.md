# domain-scanner

Проверка доменов перед заливом: ищет ту историю и те косяки в настройке, из-за
которых Google выкидывает аккаунт на верификацию.

Идея простая. Ты заливаешь пять одинаковых связок с пяти аккаунтов, три живут
неделями, две улетают на верификацию за день. Креативы те же, офер тот же —
значит разница в доменах. Сканер вытаскивает то, что Google видит о домене
снаружи, и показывает, чем «плохие» домены отличаются от «хороших».

```
$ domain-scanner -f domains.txt --footprint

lucky-cash-now.top  —  87/100  AVOID
  [#################...]  Do not put spend behind this domain.
  XX re-registered domain with a prior life in a flagged vertical (2014–2019): "Lucky Star Casino"
   X no privacy policy, terms or contact page — the exact gap that sends an account into business verification
   ! .top is a tier-3 TLD (high abuse rate)
   ! 2 hyphens in the name

northwind-shop.com  —  12/100  CLEAN
  [##..................]  No meaningful red flags found.
   ~ registered 8mo ago — under a year old
```

## Установка

Два способа пользоваться: CLI локально или веб-морда на VPS
(см. [Веб-приложение на VPS](#веб-приложение-на-vps)).

```bash
git clone <repo> && cd domain-scanner
pip install -r requirements.txt

python -m domain_scanner example.com
# либо поставить как команду:
pip install -e .
domain-scanner example.com
```

Нужен Python 3.10+. У CLI зависимости всего две: `requests` и `dnspython`.
Веб-части дополнительно нужны `fastapi` и `uvicorn` (`requirements-web.txt`).

## Быстрый старт

```bash
# один домен
domain-scanner mydomain.com

# пачка из файла + анализ общего следа + CSV для таблицы
domain-scanner -f domains.txt --footprint --csv report.csv

# только история домена (быстро, без запросов к самому сайту)
domain-scanner mydomain.com --only rdap,wayback,crtsh

# подробный вывод: info-находки, сырые данные, тайминги по каждой проверке
domain-scanner mydomain.com -v
```

`domains.txt` — по домену на строку. Можно кидать URL целиком, с `www.`, с
путём, через запятую, с комментариями через `#` — всё нормализуется:

```
https://www.lucky-cash-now.top/lp1?utm=x   # старый, улетел на верифу
northwind-shop.com
another-lander.xyz
```

## Что именно проверяется

`domain-scanner --list-checks` покажет актуальный список. По группам:

### История домена — главное

| Проверка | Что смотрит |
| --- | --- |
| `rdap` | Дата регистрации, регистратор, срок оплаты, EPP-статусы |
| `wayback` | Архив archive.org: что было на домене раньше |
| `crtsh` | Certificate Transparency: когда домен реально впервые ожил |

**Это то, ради чего всё писалось.** Типовой сценарий, который жжёт байеров:
домен зарегистрирован месяц назад, а в архиве у него контент с 2014 года.
Значит его уже использовали, бросили, и ты купил его на дропе. Репутация
привязана к имени, а не к твоей регистрации — и Google это помнит.

Сканер это ловит: сравнивает дату регистрации из RDAP с первым снимком в
archive.org и с первым сертификатом в CT-логах. Если история старше регистрации
больше чем на полгода — домен переиспользованный. Дальше он вытягивает `<title>`
старых страниц и говорит, чем домен был занят: казино, фарма, дейтинг, или
просто парковка.

Дата регистрации переписывается при перерегистрации. Первый сертификат в
CT-логах — нет. Поэтому проверок три, а не одна.

### Репутация

| Проверка | Что смотрит |
| --- | --- |
| `blocklists` | Spamhaus DBL, SURBL, URIBL, SEM — по DNS, без ключей |
| `safebrowsing` | Google Safe Browsing v4 — **нужен бесплатный ключ** |
| `virustotal` | ~90 антивирусных вендоров + категории — нужен бесплатный ключ |

Safe Browsing — единственный источник здесь, который буквально показывает мнение
самого Google о домене. Ключ бесплатный, поставить стоит.

### Инфраструктура

| Проверка | Что смотрит |
| --- | --- |
| `dns` | A/NS/MX/SPF/DMARC, парковочные NS, бесплатный хостинг |
| `hosting` | ASN и владелец сети (Team Cymru), соседи по IP |

Отсутствие MX/SPF/DMARC — слабый сигнал сам по себе, но именно по нему отличают
работающий бизнес от чистого ленда. Триста доменов на одном IP — ты наследуешь
репутацию соседей.

### Сам сайт

| Проверка | Что смотрит |
| --- | --- |
| `http` | Отдаётся ли страница, редиректы, TLS, тонкий контент, страницы политик |
| `cloaking` | Одинаковый ли контент для браузера, Googlebot и AdsBot |
| `tld` | Уровень абуза зоны |
| `naming` | Бренды в имени, тайпсквоттинг, дефисы, мусорные слова |

Отсутствие privacy policy / terms / contact — самая частая причина, по которой
аккаунт уезжает на верификацию бизнеса. Проверка ищет эти ссылки на русском,
английском, немецком, испанском, польском и турецком.

`cloaking` — диагностика: сканер тянет страницу под UA браузера, Googlebot и
AdsBot-Google и сравнивает видимый текст. Если контент разный — это ровно тот
паттерн, на который срабатывает автоматика Google. Полезно прогонять по своим же
доменам перед масштабированием.

## Общий след по пачке (`--footprint`)

Отдельно от оценок каждого домена. Ищет, чем домены в пачке похожи друг на
друга:

```
Shared footprint across the batch
   X 5/5 domains resolve to the same IP 45.11.22.33
       a.com, b.com, c.com, d.com, e.com
   X 5/5 domains share the tracking ID google_analytics:G-ABCD1234
       a.com, b.com, c.com, d.com, e.com
   ! 4/5 domains were registered on the same day (2026-07-14)
       a.com, b.com, c.com, d.com
```

Вот это, скорее всего, и есть ответ на твой вопрос. Каждый домен по отдельности
может быть чистым, но если все пять сидят на одном IP, куплены в один день у
одного регистратора и отдают побайтово одинаковый ленд с одним GA-счётчиком — то
снаружи это одна и та же операция. Как только один попадает под раздачу,
остальные подтягиваются.

Что ищется: общий IP, ASN, NS-оператор, регистратор, дата регистрации, хеш
видимого текста страницы, `<title>`, ID счётчиков (GA, GTM, Google Ads, FB
Pixel, TikTok).

## Оценка и вердикт

Каждая находка имеет вес: `low` 5, `medium` 12, `high` 22, `critical` 35. Веса
складываются, потолок 100. Одна тяжёлая находка не размывается кучей чистых
проверок: `critical` поднимает счёт минимум до 75, `high` — до 45.

| Счёт | Вердикт | Смысл |
| --- | --- | --- |
| 0–19 | `CLEAN` | Красных флагов нет |
| 20–39 | `WATCH` | Дисквалифицирующего нет, но не идеально |
| 40–69 | `RISKY` | Можно, если сначала починить перечисленное |
| 70+ | `AVOID` | Не лить |
| — | `UNREGISTERED` | Домен не зарегистрирован, оценивать нечего |

Ниже вердикта — строка `confidence`. Это доля проверок, которые реально дали
данные. Если крупные источники не ответили — вердикт помечается как
провизорный. `CLEAN` при 40% покрытия означает «не нашли», а не «чисто».

Коды выхода: `0` — все чисто, `1` — хотя бы один домен набрал `--fail-over`
(по умолчанию 40) или больше, `2` — ошибка ввода. Удобно для CI или скрипта,
который прогоняет свежекупленные домены.

## Ключи API

Всё работает без ключей. С ключами — заметно точнее. Скопируй `.env.example`
в `.env` и заполни, что есть:

```bash
cp .env.example .env
```

| Переменная | Зачем | Лимит |
| --- | --- | --- |
| `GOOGLE_SAFE_BROWSING_API_KEY` | Мнение самого Google о домене | бесплатно, щедрый |
| `VIRUSTOTAL_API_KEY` | ~90 вендоров + категории | 4 запроса/мин (соблюдается автоматически) |

Проверка без своего ключа не падает, а помечается как `skipped` и не портит
`confidence`.

## Про DNS-блоклисты — важно

Spamhaus, SURBL и URIBL **режут запросы с публичных резолверов** (8.8.8.8,
1.1.1.1). Причём Spamhaus отвечает неавторизованному резолверу `NXDOMAIN` —
это неотличимо от «домен не в списке». То есть наивная проверка тихо
рапортует «чисто», хотя её просто не пустили.

Поэтому сканер перед опросом дёргает **контрольную точку** каждой зоны
(`dbltest.com.dbl.spamhaus.org` и аналоги) — она обязана отвечать, если зона
с тобой разговаривает. Зоны делятся на три группы, видно в JSON:

- `zones_verified` — контрольная точка ответила. Молчание по твоему домену
  здесь честно значит «не в списке».
- `zones_opportunistic` — у зоны нет контрольной точки. Попадание засчитываем,
  но молчание ничего не доказывает.
- `unavailable_zones` — зона не отвечает. Не учитывается вообще.

Вердикт `blocklist.clean` выставляется, только если хоть одна зона
подтверждена. Иначе — `blocklist.no_data`: «не проверяли», а не «чисто».

### Как всё-таки достучаться до Spamhaus

На облачном VPS резолвер почти всегда упирается в 8.8.8.8 или 1.1.1.1 — в том
числе через внутренний резолвер Docker (`127.0.0.11`, он форвардит на хостовой).
Два выхода:

**Ключ (проще).** Бесплатный Spamhaus DQS: запросы идут в сервис подписчика и
отвечаются независимо от того, какой у тебя резолвер.

```bash
# https://www.spamhaus.com/free-trial/ -> получить DQS key
echo "SPAMHAUS_DQS_KEY=твой_ключ" >> .env
docker compose -f docker-compose.yml -f docker-compose.caddy.yml up -d
```

Аналогично `URIBL_KEY` для URIBL. Сканер сам переключится на зону подписчика,
в JSON это видно в `zones_using_key`.

**Свой рекурсивный резолвер.** Поднять unbound рядом и указать на него
`SCANNER_NAMESERVER`. Без регистраций, но это ещё один сервис на сервере.

Лечится указанием резолвера провайдера или локального:

```bash
domain-scanner -f domains.txt --nameserver 192.168.1.1
```

## Прочие флаги

```
-w, --workers N       сколько доменов параллельно (по умолчанию 8)
    --timeout SEC     таймаут HTTP
    --proxy URL       прокси для HTTP-проверок — посмотреть ленд из нужного гео
    --skip LIST       пропустить проверки: --skip cloaking,virustotal
    --only LIST       только эти проверки
    --json / --csv / --markdown PATH    выгрузка ('-' = stdout)
    --no-preflight    не проверять свою же связь перед сканом
```

Перед сканом сканер проверяет собственный интернет. Если исходящий HTTPS или DNS
не работают, он говорит об этом и пропускает соответствующие проверки — вместо
того чтобы записать все домены в «сайт не открывается».

## Веб-приложение на VPS

Тот же сканер, но через браузер: вставил домены, посмотрел результат, отметил
судьбу домена. Плюс история и калибровка весов по твоим же данным.

### Docker (проще)

```bash
git clone <repo> && cd domain-scanner
cp .env.example .env

# сгенерировать токен и вписать в .env
python3 -c "import secrets; print('SCANNER_TOKEN=' + secrets.token_urlsafe(32))"
nano .env

docker compose up -d --build
docker compose logs -f          # посмотреть, что поднялось
```

Порт 8000 биндится **только на 127.0.0.1** — наружу его выставляет nginx, см.
ниже. Если нужен доступ сразу без прокси, поменяй в `docker-compose.yml`
`127.0.0.1:8000:8000` на `8000:8000`, но тогда хотя бы поставь токен.

### Без Docker

```bash
git clone <repo> && cd domain-scanner
sudo ./deploy/install.sh
```

Скрипт ставит зависимости, создаёт пользователя `scanner`, разворачивает venv в
`/opt/domain-scanner`, генерирует токен, ставит systemd-юнит и проверяет, что
сервис поднялся. Токен печатается в конце — сохрани.

Управление: `systemctl {status,restart,stop} domain-scanner`,
логи — `journalctl -u domain-scanner -f`.

### Домен и HTTPS

```bash
sudo cp deploy/nginx.conf /etc/nginx/sites-available/domain-scanner
sudo sed -i 's/scanner.example.com/scanner.твойдомен.com/g' \
    /etc/nginx/sites-available/domain-scanner
sudo ln -sf /etc/nginx/sites-available/domain-scanner /etc/nginx/sites-enabled/

sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d scanner.твойдомен.com
sudo nginx -t && sudo systemctl reload nginx
```

Порт 8000 в файрволе открывать **не надо** — nginx ходит на него по loopback.
После установки nginx поставь в `.env` `SCANNER_TRUST_PROXY=1`, иначе лимит
запросов будет видеть все обращения как один клиент (127.0.0.1).

### Если на сервере уже есть другие сайты (nginx)

Конфиг рассчитан на соседство: зона лимита называется `dscan_login`, апстрим —
`dscan_backend`, пересечься с чужими именами не должно. Но перед `reload`
проверь два момента, потому что цена ошибки — падение **всех** сайтов на этом
nginx, а не только сканера:

```bash
# 1. Порт 8000 свободен? Если занят — поставь SCANNER_PORT в .env
#    и поправь порт в upstream dscan_backend.
sudo ss -tlnp | grep -E ':(8000|80|443)\s'

# 2. Нет ли уже зоны с таким именем в другом конфиге
sudo grep -rn "limit_req_zone" /etc/nginx/

# 3. И главное — синтаксис до перезагрузки
sudo nginx -t
```

`nginx -t` должен сказать `syntax is ok` / `test is successful`. Пока он этого
не сказал, `systemctl reload nginx` не запускай. И не удаляй
`/etc/nginx/sites-enabled/default` вслепую — на сервере с несколькими сайтами
он иногда содержит нужный дефолтный server-блок.


### Если на сервере уже Caddy, а не nginx

Тогда проще: Caddy сам выпускает и продлевает сертификаты, certbot не нужен.
Сканер вообще не занимает порт на хосте — Caddy ходит к нему по внутренней
docker-сети.

```bash
# 1. узнать сеть, в которой живёт Caddy
docker inspect <имя-caddy-контейнера> \
  --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}{{"\n"}}{{end}}'

# 2. прописать её в .env
echo "PROXY_NETWORK=<имя-сети>" >> .env

# 3. поднять с оверлеем: без публикации порта, но в общей сети
docker compose -f docker-compose.yml -f docker-compose.caddy.yml up -d

# 4. в Caddyfile добавить блок из deploy/Caddyfile.snippet,
#    подставив свой поддомен, и перезагрузить Caddy
docker exec <имя-caddy-контейнера> caddy reload --config /etc/caddy/Caddyfile
```

И поставь `SCANNER_TRUST_PROXY=1` в `.env` — иначе рейт-лимит увидит все
запросы как один клиент.

A-запись на поддомен должна существовать **до** перезагрузки Caddy: он сразу
пойдёт за сертификатом и будет сыпать ошибками, пока DNS не разойдётся.

### Интерфейс

Три вкладки:

- **Скан** — вставляешь домены, видишь прогресс, разворачиваешь карточку с
  находками. Внизу — общий след по пачке. Экспорт в CSV/JSON/Markdown.
- **История** — прошлые сканы и список доменов. Тут же выпадашка «что стало с
  доменом»: живёт / верификация / бан.
- **Калибровка** — ради чего всё это. Для каждой находки показывает, как часто
  она встречалась у выживших доменов и у проблемных. Колонка **lift** — разница
  между ними. Высокий lift = признак реально предсказывает проблемы. Около нуля
  = шум, вес в `models.py` можно снижать.

Калибровка пустая, пока не отметишь судьбу доменов. Отмечай — на своих данных
за пару месяцев она скажет о твоей вертикали больше, чем любые дефолтные веса.

### Настройки веб-части

Всё через `.env`, полный список с комментариями — в `.env.example`.

| Переменная | По умолчанию | Что делает |
| --- | --- | --- |
| `SCANNER_TOKEN` | пусто | Токен доступа. **Пусто = вход без пароля** |
| `SCANNER_TRUST_PROXY` | `0` | Ставь `1` за nginx — иначе рейт-лимит общий на всех |
| `MAX_DOMAINS_PER_SCAN` | `50` | Потолок доменов за скан |
| `SCANNER_RATE_LIMIT` | `20` | Сканов на клиента за `SCANNER_RATE_WINDOW` секунд |
| `SCANNER_WORKERS` | `8` | Доменов параллельно внутри одного скана |
| `SCANNER_MAX_CONCURRENT_SCANS` | `2` | Сканов одновременно |
| `SCANNER_NAMESERVER` | системный | Резолвер для блоклистов (см. раздел выше) |
| `SCANNER_PREFLIGHT` | `1` | Самопроверка связи |

### API

Всё, что делает интерфейс, доступно и curl-ом. Токен — в заголовке
`X-Auth-Token` или `Authorization: Bearer`. Интерактивная схема: `/api/docs`.

```bash
H="X-Auth-Token: твой-токен"
API=https://scanner.твойдомен.com

# запустить скан
curl -s -X POST $API/api/scans -H "$H" -H 'Content-Type: application/json' \
  -d '{"domains":["a.com","b.com"],"label":"залив 14.07"}'

# забрать результат
curl -s $API/api/scans/<scan_id> -H "$H"

# выгрузить CSV
curl -s "$API/api/scans/<scan_id>/export?format=csv" -H "$H" -o scan.csv

# отметить судьбу домена
curl -s -X PUT $API/api/domains/a.com/outcome -H "$H" \
  -H 'Content-Type: application/json' -d '{"outcome":"verification"}'
```

`GET /api/health` открыт без токена (для мониторинга) и показывает состояние
связи сервера — если `status: degraded`, значит VPS сам не достучался наружу и
часть проверок пропускается.

### Бэкап

Всё лежит в одном файле SQLite:

### Безопасность — что уже сделано и что на тебе

Сделано в коде:

- **SSRF закрыт.** Сканер ходит по доменам, которые ему дают, — а на VPS это
  прямая дорога к `169.254.169.254` (метаданные инстанса) и во внутреннюю сеть.
  Любой хост, который резолвится в приватный, loopback, link-local или CGNAT
  адрес, отклоняется. Редиректы разворачиваются вручную и **каждый хоп
  проверяется отдельно** — иначе чужой домен увёл бы сканер внутрь 302-м.
- Токен сравнивается через `secrets.compare_digest`, кука `HttpOnly` +
  `SameSite=strict`.
- Рейт-лимит на запуск сканов, потолок доменов на скан.
- Контейнер бежит от непривилегированного пользователя, `no-new-privileges`,
  пишет только в `/app/data`. systemd-юнит — с `ProtectSystem=strict`.
- `robots.txt` закрывает индексацию.

На тебе:

- **Поставь `SCANNER_TOKEN`.** Без него любой, кто найдёт URL, будет запускать
  сканы с твоего сервера от твоего IP.
- Поставь HTTPS. Токен ходит в заголовке, по http его видно.
- Не открывай 8000 в файрволе.

## Настройка под себя

Данные вынесены в JSON, правь под свои вертикали:

- `domain_scanner/data/tld_risk.json` — тиры зон
- `domain_scanner/data/keywords.json` — бренды, чувствительные слова, мусорные
  слова, и `brand_domains` (официальные домены брендов, чтобы `google.com` не
  считался подделкой под Google)
- `domain_scanner/data/registrars.json` — регистраторы, парковочные NS

Пороги (что считать «свежим» доменом, сколько соседей по IP это «много»)
лежат в `domain_scanner/config.py`.

Новая проверка — это функция с декоратором:

```python
from domain_scanner.checks.base import register, ScanContext
from domain_scanner.models import CheckResult

@register("mycheck", order=60, description="...", transport="http")
def check_mine(ctx: ScanContext) -> CheckResult:
    result = CheckResult(name="mycheck")
    result.add("mycheck.problem", "medium", "человекочитаемое описание")
    return result
```

Импортируй модуль в `domain_scanner/checks/__init__.py` — дальше он сам
подхватится в CLI, скоринг и все форматы вывода. `transport` (`none`/`dns`/
`http`) говорит, что делать, если этого транспорта нет.

## Честные оговорки

**Это эвристика, а не приговор Google.** Никакого доступа к внутренним сигналам
Google Ads нет ни у кого снаружи. Сканер собирает то, что видно публично, и
взвешивает по тому, что обычно коррелирует с проблемами. Домен с оценкой 0 может
улететь на верификацию, домен с 60 — прожить полгода.

**Веса подобраны руками, а не обучены на данных.** У тебя есть то, чего нет
здесь: история твоих собственных доменов. Прогони через сканер и те, что умерли,
и те, что живут, сравни находки — и подкрути веса под свою вертикаль. Для этого
`--json` и `--csv`.

**Верификация бывает не из-за домена.** Новый платёжный метод, резкий скачок
бюджета, гео аккаунта, вертикаль, возраст самого аккаунта — всё это триггерит
проверки независимо от домена. Сканер закрывает только доменную часть.
